## 3. 三个必须今天定的决策点（**先看完再动手**）

### ① 到位门：值已定（1.2），但**必须显式写进提交命令**

| 值 | 出处 | 说明 |
|---|---|---|
| **1.2°（yaw）/ 1.92°（pitch）** | 脚本缺省 `run_measure.sh:180/193/204/237` 的 `${DSH_ARRIVE_DEG:-1.2}` | **H6 低/中两速全中就是在这个值下打出来的** ⇒ 已验证 |
| 0.8° | 代码缺省 `task_2.cpp:161` | 直跑 `./build/task_2`（不经脚本）时的缺省 ⇒ **与验证形态不一致**；0.8° 连续 3 帧达标率实测仅 1.5%（几乎哑火） |

⇒ **规则：提交命令必须显式写 `DSH_ARRIVE_DEG=1.2`**，不依赖任何缺省——提交是直跑二进制，代码缺省是 0.8°。
⇒ pitch 门限不用管：它自动跟 yaw × 1.6（task_2.cpp:167）= 1.92°，与验证时一致；除非显式给 `DSH_ARRIVE_PITCH_DEG`。
⇒ **不需要**再补 1.2 的复核场：它就是 H6 的形态（H6 走脚本 ⇒ 脚本缺省覆盖代码的 0.8 ⇒ 实际 1.2/1.92）。

### ② 人工开火门：脚本会把它硬置 0

`tools/onsite/run_measure.sh` 的四个子命令里都写着：

```
export DSH_FIRE_KEY_ENABLE=0   # 硬置 0：继承来的 DSH_FIRE_KEY_ENABLE=1 也不许把枪口关掉（10-23 现场要求）
```

⇒ **用 `run_measure.sh spin` 去提交 ⇒ 人工门是关的** ⇒ 10 发额度只剩 `submit.yaml` 的程序截断这一层。  
⇒ **提交必须直跑 `./build/task_2`，不要过脚本**（见 §4 开考命令）。
⇒ 附注：`DSH_FIRE_KEY_ENABLE` 的硬置**有意保留**（10-23 现场决定：测量时不让继承来的 1 把枪口关掉），
提交日不改；提交命令显式写 `DSH_FIRE_KEY_ENABLE=1` 即可，不经脚本就不受它影响。

### ③ `run_measure.sh spin` 的 lead 缺省是 0.100，不是 0.024

脚本第 199 行：`export DSH_LEAD_MID="${lead:-${DSH_LEAD_MID:-0.100}}"` —— **脚本把缺省写成 0.100**（代码缺省是 0.024）。  
⇒ 若用脚本跑而没显式带 `DSH_LEAD_MID=0.024`，**lead 会是 0.100 = 过补约 76 ms**（中速必飞）。  
⇒ **已于 10-24 09:35 修复**：冻结包 0935 的 `run_measure.sh:199` 缺省已改为 **0.024**（与代码一致）⇒ 该坑消除。
⇒ 结论仍是：**提交一律直跑二进制**（不经脚本），但脚本现在也可用于测量而不会带偏 lead。

### ④ 提交前必须清掉 shell 里的 lead 环境变量（`DSH_LEAD` 一票覆盖两档）

代码 `task_2.cpp:299`：`if (v != nullptr) { lead_low_s = lead_mid_s = lead_s = atof(v); }`
⇒ **只要环境里存在 `DSH_LEAD`，它会把 LOW 和 MID 一起覆盖**（历史兼容语义，脚本的 slope/sign 子命令正是靠它做单值标定）。

风险：调试文档里到处教 `DSH_LEAD=0.09 ~/run_measure.sh …`，若 shell 里曾 `export` 过 `DSH_LEAD`，
提交时 **LOW 档的 0.000 会被覆盖成那个值** ⇒ 低速档过补 57 ms（低速本已验证 0.000 为最优）。

⇒ **提交命令用 `env -u` 逐个清掉**（已写进 §4）：`-u DSH_LEAD -u DSH_LEAD_LOW -u DSH_LEAD_MID
-u DSH_LOCK_MODE -u DSH_AMBUSH`。
  只清 `DSH_LEAD` 不够——**`DSH_LOCK_MODE=1` 才是"开不了火"的元凶**，必须一起清掉。
⇒ 开考前自检一行：`env | grep DSH_`（除随后显式给出的 3 个外应为空）。
⇒ 这也是"提交形态 = 验证形态"的最后一环：H6 走脚本时 `DSH_LEAD` 只在脚本进程内存在，
提交是直跑二进制，继承的是**你的 shell**——两者环境不同，必须显式清。
