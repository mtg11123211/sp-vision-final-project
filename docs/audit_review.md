## 1. ① 追着一块板连续打 —— 原报告成立

三道闸（`facing ≤ 25°`、`plate_armed` 每帧现算、`interval 0.2 s`）叠起来，稳态旋转下**每块板每圈 1 发**成立，时序表算术正确（25°/4 = 0.109 s、35°/4 = 0.153 s、(90−25)/4 = 0.284 s，3.5 Hz）。

### 修订 8：洞 2 降级

原报告说「A→B→A 跳板时会把刚打过的板再打一发」。**稳态下不可达**：四块板互隔 90°，任一时刻最多一块落在 ±25° 窗口内；而换板还要求另一块 `|facing|` 好 5°（`:399`）。两块同时进窗口是几何上不可能的事件。

只有在**靶子反向**或 **EKF 角度跳变**时可到达——而反向时那块板确实是重新转进窗口的，打第二发在语义上是「新的一次通过」，不算违规。

**结论：低风险，不建议现在加「已打过的板集合」。**

### 修订 9：`:556` 不是死代码，是冗余

```
:556  plate_armed = false;          // 开火后立刻退膛
:413  plate_armed = target_static || (aim_id != last_fired_plate) || (|facing| > 35);
```

下一帧确实会重算，但重算用的是**同一帧刚更新的** `last_fired_plate = aim_id` 和「刚开火时 facing 必然 < 25°」，算出来仍是 `false`。**值与保险意图一致，行为正确。**

原报告的「行为没问题」对，「注释与行为不一致」过重——它是冗余行，不是坑。

### 洞 1 的修法（原报告只提风险，没给方案）

```cpp
// 现在
const bool target_static = std::abs(x[7]) < 0.5;
// 建议
static int still_frames = 0;
still_frames = (std::abs(x[7]) < 0.15) ? still_frames + 1 : 0;
const bool target_static = still_frames >= 10;   // 连续 10 帧 ≈ 0.16 s
```

两个改动：阈值 **0.5 → 0.15**（避开 w 反向穿越区间），加 **连续 10 帧**（避开起步爬升）。

## 2. ② 锁中心的板 —— 原报告两个硬伤，一真一假

### 修订 10：硬伤 1 不成立

原报告说「候选集是在 EKF 预测的 4 块板上取的，可能包含当前看不见的板」。

**几何上不成立**：`facing_of` 算的是「板外法线与视线夹角」（`:381-383`），四块板里 `|facing|` 最小的一定是**最正对镜头**的那块——正对镜头就意味着看得见。这个值最大不超过 45°（两块板各 45° 的临界点），35° 以上的板在 1080p 下依然有足够像素被检测到。

真正的风险不是「瞄到看不见的板」，而是下面这条：**瞄准的和 HUD 画的不是同一块**，导致人无法判断它锁了谁。

### 修订 12：迟滞确实失灵，而且原因比原报告说的更具体

原报告说「5° 迟滞相对 `last_id` 而不是上一帧选中的板」。核代码，**成立**：

```cpp
:373  int aim_id = target.last_id;          // ← 每帧重置成 last_id
:399  if (best_id != aim_id && best_facing + 5.0 < std::abs(facing_of(xyza_list[aim_id]))) aim_id = best_id;
```

因为 `:373` 每帧把 `aim_id` 重置成 `target.last_id`，`:399` 的比较基准永远是 **`last_id` 的 facing**，不跨帧记忆。所以：

- 「只打最正对的板」这件事**仍然生效**（另一块必须好 5° 才被选中）；
- 但「防止临界来回跳」**没生效**——在两块板 facing 相差 ±5° 的窄带里，`aim_id` 会跟着 `last_id` 翻，选板闪烁。

**影响面**：只在临界点附近 ±5°（约 0.15 s 的窗口），表现为那一瞬间的瞄准点在两块板之间跳一下。修改很小：把 `aim_id` 提到循环外（`static int aim_id`），让比较基准是上一帧真正的选择。

## 3. ③ 板往右转却锁左边 —— 原报告结论对，推导错

### 修订 13：0.9~1.2° 不是按 4 rad/s 算出来的

原报告写：

```
帧龄 25 ms + 同包 1 帧 17 ms + 出弹延迟 20~40 ms = 62~82 ms → 4 rad/s 下 0.9~1.2°
```

**这句自相矛盾**：4 rad/s × 62 ms = **14.2°**，不是 0.9~1.2°。0.9~1.2° 对应的是 **0.25 rad/s ≈ 14.3°/s**——也就是「板在相机里的视在角速度」，不是目标自转角速度。

正确写法：

```
视在角速度 = r·|w| / d ≈ 0.2 × 4 / 3.15 ≈ 0.25 rad/s ≈ 14.3°/s
62~82 ms × 14.3°/s = 0.9~1.2°
```

数字没错，**理由必须换成视在角速度**，否则读者会以为「4 rad/s ⇒ 几十毫秒就是十几度」，把量级估错 15 倍。

### 修订 14：这个量级只值半个靶宽

0.9~1.2° 对 ±1.29° 的板半宽，是「打在板的后半边」而不是「脱靶」。

所以 ③ 必须分清两种现场现象：

| 现象 | 量级 | 成因 | 修法 |
|---|---|---|---|
| 「锁在后面」 | 0.5 个靶宽 | 延迟未补 | 开 `DSH_LEAD=0.057` |
| 「差好几块板」 | 5~15° | 指向误差（零位、facing 约定、EKF 跳变） | 不是 lead 能解决的 |

原报告把两种混成一句「相当一部分弹会落在板的后半边甚至出板」，会让读者以为开个 lead 就能解决全部偏移。

**判据**：`grep 'assoc='` 长期 ±150° ⇒ facing 约定反了（删 `:383` 的 `+ M_PI`）；`assoc` 在 0~40° 而弹着点仍差几块板 ⇒ 查零位与 `errY`，不是 lead。

## 4. ④ 无条件开火 —— 原报告成立，两处要补

### 修订 15：是 9 个条件，不是 8 个

```cpp
:533  const bool would_fire = has_detection && stable && interval_ok && rounds_ok && mode_ok && !holding && plate_ok;
:535  const bool fire = would_fire && arrive_ok && !latency.step_enabled();
```

第 9 条 `!latency.step_enabled()`：**阶跃测试期间强制不放弹**。漏掉这条，`DSH_DTEP_DEG` 打开的那场会被误判成「哑炮」。

### 修订 17：NIS 有两个阈值，原报告只看到一个

| 变量 | 值 | 用途 | 位置 |
|---|---|---|---|
| `nis_threshold` | 9.488（4 自由度 95%） | 只用于统计「最近失败率」 | `extended_kalman_filter.hpp:50`，`.cpp:72,77` |
| `nis_reject_threshold` | 16.27（4 自由度 99.7%） | **真拒收**：回滚 `x/P` 并返回 false | `target.cpp:306,310-325` |

「永不开火」这个坑是**两个一起**才堵上的：

1. 阈值从 1.5 提到 9.488 ⇒ 正常帧不再被记成失败（4 维 NIS 均值就是 4，1.5 会让 83% 的帧超限）；
2. `target.cpp:317-325` 在拒收后把刚压进窗口的那个 `1` 退掉，并重算失败率。

只做第 1 条，一次拒收风暴照样能把失败率顶到 1.0。

### 修订 18：窗口长 100 帧 ≈ 1.6 秒

`extended_kalman_filter.hpp:43` `window_size = 100`。配合 58 fps：

- 拒收风暴的后果不是「永久不开火」，而是**最长 1.6 秒不开火**；
- 换板、前哨站第四块板混入的瞬间，会有 1~2 秒的「有目标但不发弹」——**这是设计代价，不是 bug**，现场不要当成哑炮去改代码。

### 修订 16：额度漏洞要加条件

原报告说「电控不执行时软件也以为打了一发（`rounds_this_stage++`）」。实际代码：

```cpp
:558  if (!bullet_count_alive) rounds_this_stage++;
```

只有**电控不回报发弹数**时才自计。电控正常回报时，用它的计数。所以这条漏洞成立的前提是 `bullet_count_alive == false`——先看日志里 `bullet_alive=` 那一项再下结论。

## 6. 优先级重排

原报告的 4 条，我按「对命中率的实际贡献 ÷ 代价」重排：

| 新序 | 动作 | 解决 | 代价 | 依据 |
|---|---|---|---|---|
| **1** | 确认挡位是 `AUTO_AIM`；`DSH_ARRIVE_DEG` 用缺省 **0.8** 起步（1.2 只在应急时用） | ④ 两个静默杀手 | 一条环境变量 | `mode_ok` 为假会被 `:469` 静默拦下；0.8° 骑在实测 0.64~1.51° 中间 |
| **2** | `DSH_LEAD=0.057` 打开，并用斜率法验符号 | ③ 的「锁在后面」 | 一条环境变量 | 先验符号（10 秒、不发弹），再定值 |
| **3** | HUD 打出 `aim_id` 与 `facing` | ② 的硬伤 2 | 小改 | 现在准星恒在中心、线画 `chosen`，人根本看不出锁了谁 |
| **4** | `target_static` 加连续帧 + 阈值降 0.15 | ① 洞 1 | 小改 | 见 1.3 |
| **5** | `aim_id` 提到循环外（真迟滞） | ② 的临界闪烁 | 小改 | 见修订 12 |
| **6** | 把 lead 标定到 0.07~0.09 | ③ 的剩余误差 | 3 发 + 斜率法 | **不要直接填 0.08**，那是猜 |

与原报告的两处分歧：

- 原报告把「lead 标定到 0.07~0.09」排第一 —— **不同意**。lead 的有效量只有 0.83°，即使全对也换不来命中率；排第一的必须是「能不能打出去」（挡位 + 门限）。
- 原报告说「门限别一上来就 1.5」—— 同意，并补一句**上限**：门限 1.5° 已超过 ±1.29° 的板半宽，等于**允许注定打不中的弹放出去**。合理区间 0.8~1.2。

## 7. 两条新策略的真实覆盖面

| 策略 | 能补 | 不能补 | 补充 |
|---|---|---|---|
| 只打低位靶 | 高板的俯仰系统偏差；低位靶的窗口更接近画面中心 | ③ 的 lead、④ 的门限 | **发射机会减半**：4 块板里只剩 2 块低位，弹频 3.5 Hz → 1.75 Hz |
| 按住 F 才开火 | ④ 的额度浪费（人决定何时扣扳机） | 精度一个都不解决 | 建议 `toggle` 而不是 `hold`：手腕抖一下就错过 218 ms 的窗口 |

两条策略**互不相关**——低位靶解决的是俯仰，按住 F 解决的是授权，都不是「锁错边」。
