### lead 的取值判断（**唯一需要动脑的地方**）

`task_3.cpp:81` 的 `DSH_LEAD` 缺省 **0**。两种算法：

- **照抄物理链**：B1(25) + B2(32) + B3(20~100) + 同包 1 帧(17) ≈ **0.09~0.17 s**
  ⇒ 前哨站几何（2.5 rad/s、r=0.2765、3 m ⇒ 视在角速度 12.6°/s）下补 0.09 s = 1.18°，接近板半宽 1.29°，补多了必飞
- **照抄 task2 的实测值 0.024**：但那是 **task2 在 1.2° 到位门控下**标出来的——门控把云台滞后"等掉"了，
  所以 task2 只剩 0.024 的残余要补；**task3 没有门控**，照抄 0.024 会欠补

⇒ **建议：task3 提交时 `DSH_LEAD` 保持 0（代码缺省）**。理由：task3 是 **12 Hz 连发 30 秒、按命中数计分**，
命中数量远重于单发精度；欠补 0.72°（半个板半宽）仍落在板内，而补错方向（过补 1.2° 以上）会系统性打到板外。
⇒ 若时间充裕且想标定：用 `lead_solve.py` 的斜率法在 task3 靶上跑两档各 3 发（与 task2 同法），
但**别在正式提交时才第一次试**。

### task3 的操作序列（**只编译，不改代码**）

```bash
# 车机
cd ~/fp_aim && touch src/task_3.cpp && cd build && make -j2 task_3 2>&1 | tail -3
```
```bash
# 先干跑 6 秒自检（挡位/参数/能出弹）
cd ~/fp_aim && timeout 6 ./build/task_3 configs/sentry.yaml 2>&1 | grep -E '预测时域|offset|挡位|射出'
```
```bash
# 正式提交（12 Hz 连发，30 秒计时；人工门默认关，靠连发拿命中）
cd ~/fp_aim && env -u DSH_LEAD -u DSH_FIRE_DELAY -u DSH_FIRE_KEY_ENABLE -u DSH_LOW_PLATE \
  ./build/task_3 configs/sentry.yaml 2>&1 | tee logs/SUBMIT_T3_$(date +%m%d_%H%M).log
```

要点：
- `env -u` 清掉 `DSH_LEAD`（task3 缺省就是 0，清掉更干净）、`DSH_FIRE_DELAY`（task3 会警告它没进补偿）、`DSH_FIRE_KEY_ENABLE`（task3 人工门缺省关；若想开门需显式给 1）、`DSH_LOW_PLATE`（task3 没这个机制，留着无害但别继承）
- **task3 走 `sentry.yaml` 的 task3 段**（12 Hz、不限发、不要求 AUTO_AIM）
- 30 秒计时 ⇒ 12 Hz × 30 ≈ 360 发；按命中计分 ⇒ **别为了"打得准"去调参数**，别错过计时窗口
- 结束后拷回 `logs/SUBMIT_T3_*.log` 与 `summary_*.txt`，按 §1 ②③ 出记录
