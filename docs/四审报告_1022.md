## 二、硬缺口清单（按"不修必翻车"排序）

### ★1. lead_solve.py 符号 bug —— M4 的解算器是坏的（实跑证实）

`tools/lead_solve.py:170`：`T = lead_a + off_a / k_use`。

物理模型：off（正 = 沿转动方向超前）= k×(L−T) ⇒ **正确公式 T = L − off/k**。
用它自己的 docstring 用例（lead 0.057 → off −30 mm；lead 0.171 → off +61 mm；k=800 mm/s）：
- 数学正解：T = 0.057+30/800 = **94.5 ms**；另一档 0.171−61/800 = **94.9 ms** —— 两档互证 ✓
- 代码实跑输出：**T = 19.4 ms**（`DSH_LEAD=0.0194`）——错 5 倍，且恰好在 0.02 合理域下限附近、警告都不触发

后果：M4 按 0.057/0.171 两档打 6–10 发弹，解出的 lead 把欠补从真实值变成 75 ms —— **标定必然失败 + 浪费最稀缺的弹药**（三个任务的实弹测试机会都有限，task2 的每一发练习弹都要计入总预算，见 §五发弹预算）。minimax 自己在 :51 写了"只做过语法检查、没实跑过"，它知道风险但没人验。

修法（5 分钟）：
```python
T = lead_a - off_a / k_use          # :170 符号修正
T_b = lead_b - off_b / k_use        # 新增：B 档独立解
if abs(T - T_b) / max(1e-9, abs(T)) > 0.15:
    print("⚠ 两档解出的 T 差 >15% ⇒ 读数或转速不一致，别用")   # 新增自检
```
注：k_meas/k_theory=1.00 的斜率自检是对的（斜率方向没反），错的只有"反解 T"这一步——这正是语法检查抓不到、一次手算就能抓到的 bug 类型。

### ★2. 中挡 9 rad/s 全程无验证 —— 与"一次提交机会"冲突的最大单点

M0–M10 全部围绕低挡设计：slope 模板 `omega = 4` 硬编码，M2/M6/M7/M8 都在低挡。
- `DSH_LEAD=T` 两挡通用（T 是物理时延，与 ω 无关）✓
- **但到位门限不通用**：errY 随转速增大（跟踪滞后 31.8 ms 是固定相位 + 震荡超调 252%），低挡 errY 定的门限中挡可能完全不适用；中挡正对窗口本就只有 ~97 ms（5–6 帧），叠加"连续 3 帧"门控后可能整圈无弹
- **中挡的第一次真实发弹 = 正式提交**（每挡各算命中、每任务一次提交机会）

修法：M8 之后插入 **M8.5 中挡验证场**（流程文档 + 一条命令）：
```bash
DSH_ARRIVE_DEG=<M5 定的值> DSH_LEAD=<M4 定的 T> DSH_LOW_PLATE=0 DSH_FIRE_KEY_ENABLE=0 \
  ./build/task_2 configs/standard.yaml        # 靶机切中挡（5–9 rad/s），先干跑 30 s
```
判据：fire-gate 行 `blocked` 不持续涨、`arrive` 偶尔 True。**干跑通过后只试 2–3 发**（验证"能出弹、落点同侧"即可，不求命中，省弹给正式提交）。若整圈无 arrive：
① `DSH_ARRIVE_FRAMES=2`（应急）→ ② `DSH_ARRIVE_DEG=1.5`（超板半宽，比零发强）→ ③ 接受中挡 0/10、保住低挡 + 角速度 40 分里的其余部分。

### ★3. M5 门限的定量可行性 —— 0.8° 几乎必然哑火，1.2° 顶格也只有 25%

用基线 10-20 实测（lat_1510.csv，n=2686，门控关状态）复算 |cmd−fb| 的达标率：

| 门限 | 单帧达标 | 连续 3 帧达标 |
|---|---|---|
| 0.8°（当前缺省） | 8.0% | **1.5%** |
| 1.0° | 19.8% | 8.5% |
| **1.2°（M5 上限）** | 40.0% | **25.3%** |
| 1.5° | 62.9% | 48.3% |

M5 规则"errY×1.2~1.5、上限 1.2°"：若新代码 errY 均值仍 ~1.3°（p50 实测 1.30°），门限到顶 1.2° → 连续 3 帧达标 25% → 叠加 0.2 s 间隔 + ±25° 面朝窗口（4 rad/s 下 0.22 s）+ 一块板一发，实际弹频估计 1–1.5 Hz（判据表理论 2.55 Hz）。**10 发能打完但每一发都在云台没完全到位时出去**。根源是云台震荡（阶跃 T90 48 ms、超调 +252%）——lead 补相位、门限放宽只让弹出膛，不提高单发精度。
修法：不修代码，修预期——M6 基线命中数按 1.2° 出弹状态校准；M6 若 blocked 持续涨，预案是 `DSH_ARRIVE_FRAMES=2` 而不是继续放宽门限（判据表 §6 已写但 M5 没引用）。

## 四、对 minimax 实现思路与脚本的总评

**思路（方案①）是对的**：把三段时延合成 `DSH_LEAD` 一个旋钮、`DSH_FIRE_DELAY` 降级为记录值，从结构上消灭双补；M0–M10 的顺序约束（M1 零位最先、M3 符号先于 M4、两挡转速一致）在方法论上无懈可击；判据表 §6 的量化（视在角速度 14.55°/s ≠ 靶柱相位 229°/s、板半宽 1.23°、官方国赛命中率参照）是真功夫。

**脚本质量两极**：
- `latency_report.py` —— **实跑通过**，31.8 ms 完整复现（lat_1510.csv 互相关 r=0.71；DS4.1 质疑"step_1508 13 Hz 做不了互相关"是找错了数据源，31.8 ms 从来不是从 step_1508 算的）。顺带暴露一个对话里没强调的数：**yaw 阶跃超调 +252%**——这是 errY 压不下去的根源。
- `run_measure.sh` —— 结构好（8 个子命令、每场自动带 TAG/SUMMARY、冒烟测试过两个真 bug），preflight 只编 task_2+keytest 意味着 task_3 编译错全程静默。
- `lead_solve.py` —— **核心公式符号反**（见 ★1），且缺两档交叉验证。这正是"语法检查 ≠ 正确性验证"的教科书案例。
- `parse_session.py` —— 判读逻辑健全（不锚定行首的 logger 前缀处理是对的），A2/C3 数据链自动，B1/B2 需手动。

**工作纪律**：全程"原工程零改动 + 哈希自证"诚实可信；"没实跑"的风险每次都主动声明——但声明不能替代验证，这次实跑抓出的符号 bug 就是证据。
