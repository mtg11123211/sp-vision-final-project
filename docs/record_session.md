# 有录像的那一次：怎么跑

> 四场、每场 ≤15 秒、**一场只改一个变量**。每场同时开三个记录开关。每场结束记 5 个数。
> `DSH_LEAD` 单位是**秒**（57 ms = 视觉 25 + 云台 32），缺省 0 = 不补。

---

## 一、三个开关 + 一份日志

| 开关 | 写到 | 里面有什么 | 为什么必须要 |
|---|---|---|---|
| `DSH_RECORD_DIR` | `recordings/run_<tag>/` | `frames.csv`（四元数、bullet_count、mode、bullet_speed）+ 每帧 jpg | 时间轴：什么时候开的火、云台转多快 |
| `DSH_DET_CSV` | `logs/det_<tag>.csv` | 每帧每块板的框、颜色、置信度、画面中心 | **决定性**：开火那一刻板在画面里偏多少像素 |
| `DSH_LAT_CSV` | `logs/lat_<tag>.csv` | 每帧取帧/解算/发送的时间戳 | 视觉与串口延迟 |
| `tee` | `logs/<tag>.log` | `fire-gate` / `arrive` / `errY` / 挡位 | 门控和跟随误差的唯一来源 |

少了 `DSH_DET_CSV` 这场基本白录 —— 只有云台姿态，没法回答“瞄准点当时偏在哪”。

---

## 二、四场（12 发）

| 场次 | 靶子 | `DSH_LEAD` | 目的 |
|---|---|---|---|
| `A_static` | 静止 | 不设（0） | 确认录像不影响命中、零位没问题 |
| `B_lead0` | 旋转 | 不设（0） | baseline：偏多少 |
| `C_lead57` | 旋转 | `0.057` | 物理正解（视觉 25 + 云台 32 ms） |
| `D_lead171` | 旋转 | `0.171` | 3 倍，测斜率；判断 lead 有没有用 |

**A 场不能省**：录像会掉帧到 ~45，要先确认“开着录像也能打中静止靶”，否则后面三场的数据全部可疑。

> 注意：录像模式下算出的延迟都偏大（帧率 58→45），C/D 两场只用来**判方向、判单调**，数值以关录像那几场为准。

---

## 三、每场的命令（改 tag 和 LEAD 即可）

```bash
cd ~/fp_aim
T=A_static
mkdir -p recordings/run_$T
```

```bash
DSH_RECORD_DIR=$HOME/fp_aim/recordings/run_$T \
DSH_DET_CSV=logs/det_$T.csv \
DSH_LAT_CSV=logs/lat_$T.csv \
DSH_ARRIVE_DEG=0.8 \
./build/task_2 configs/standard.yaml 2>&1 | tee logs/$T.log
```

打 3 发，Ctrl-C 停。下一场把 `T` 换成 `B_lead0`，并把 `DSH_LEAD=0.057` 之类加进上面那串环境变量。

> 用 `./build/task_2` 直接启动，不用 `run2.sh`，因为它 `exec` 之后不方便确认环境变量有没有传进去；
> 启动时 `runs` 目录和 `det/lat` 文件都是全新创建的，一眼能看出三个开关都生效了。

---

## 四、每场结束立刻记这 5 个数（写在纸上）

```bash
tail -3 logs/$T.log
```

```bash
grep -o '挡位 = [A-Z_]*' logs/$T.log | sort | uniq -c
```

| # | 数 | 从哪来 |
|---|---|---|
| 1 | `[Recorder] 已录制 N 帧，频率 XX 帧每秒` | 帧率，<50 就要标“录像模式” |
| 2 | 打了几发 | 目视 / 弹壳 / `bullet_count` 增量 |
| 3 | 中几发 | 目视 |
| 4 | 弹着点方向 + 几个板宽 | 目视，135 mm = 1 板宽 |
| 5 | 挡位是否全程 `AUTO_AIM` | 上面那条 grep，出现 `IDLE` 这场作废 |

## 五、磁盘（开录前先看）

每场 300–450 MB，四场约 **1.5 GB**。

```bash
df -h ~ && du -sh ~/fp_aim/recordings
```

不够就先 `bash tools/onsite/disk_guard.sh --keep 1`。

## 六、两个坑

1. **录像会把 58 fps 压到 ~45（−23%）**。所以这场算出来的所有延迟都标“录像模式”，
   最终参数必须**关录像复验 3 发**才算定稿。
2. **一场一个进程一个目录**。Ctrl-C 之后再开下一场，别在同一个目录里续录，否则帧号和时间轴混在一起，离线分不开。

---

## 七、回来给我什么

四个 `tag` + 上面 5 个数，或者直接把 `logs/det_*, logs/lat_*, logs/*.log` 和四个 `frames.csv` 打成小包（几 MB，不含 jpg）。
jpg 只有在要看“子弹从哪边掠过”时才需要，到时候再挑单场拉。

我这边跑四件事：

| 脚本 | 给出什么 |
|---|---|
| `analyze_frames.py` | `\|ω\|`、bullet_count 增量、挡位、帧率、开火时刻 |
| `latency_report.py` | 视觉 p50、串口、云台互相关滞后 |
| `aim_error.py`（新写） | 每发开火那一刻：板中心 − 画面中心 = 多少像素 = 多少度 |
| `shot_fit.py` | 12 发落点的拟合斜率，和上面那条互相印证 |

`aim_error` 是关键量：它直接告诉你“开火瞬间瞄偏了几度”，跟 lead、跟延迟都无关，是**瞄准链本身的误差**。
自标定方式：135 mm 的板在 d 米处占 W 像素 ⇒ 每像素 = 135/(d·W) 弧度，不需要标定文件。

---

## 八、这四场能定什么

| `aim_error` 的表现 | 结论 |
|---|---|
| A 场小（<0.3°）、B/C/D 也小，但落点偏 | 瞄准对、弹道偏 → 查弹速/俯仰/机械 |
| B 大、C 小、D 更小（随 lead 单调变） | 就是时间型误差 → 按 C/D 之间二分定系数 |
| A/B/C/D 都一样大 | 常值型 → 回去查零位（这时候第 1 步的静止靶才真正派上用场） |
| 每发之间抖得厉害 | 随机型 → 云台跟随/门控，调 lead 无用 |
